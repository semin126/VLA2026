# 학생 연구 안내: 기숙사 로비의 택배를 어떻게 분류할까?

수업용 한 장 요약은 [여러분이 결정할 여섯 지점](RESEARCH_DECISIONS.md)입니다.

이 자료의 목표는 여러분이 **작은 질문 하나를 정하고, 공정한 실험으로 답하며, 답의 범위를 설명하는 것**입니다. 어려운 모델을 실행했다는 사실과 좋은 연구를 수행했다는 사실은 다릅니다. 반대로 익숙한 방법을 쓰더라도 아직 확인하지 않은 조건과 한계를 체계적으로 밝히면 의미 있는 탐구가 됩니다.

이 안내의 가설과 실험표는 **설계 예시**입니다. 이미 얻은 결과나 제출할 정답이 아닙니다. 실제 연구에서는 여러분이 질문과 판단 근거를 기록하고 수정해야 합니다. 함께 사용할 빈 양식은 [연구 워크시트](WORKSHEETS.md), 실행 절차는 [학생 실험 시작 안내](../STUDENT_RESEARCH.md)에 있습니다.

## 1. 우리가 만들려는 것과 알아내려는 것

공학적 목표는 “무작위로 쌓인 택배를 각각 정해진 구역에 옮겨 분배하는 로봇”입니다. 이것을 완성하려면 수취인·구역 인식, 물체 위치 추정, 집을 순서 선택, 파지, 운반, 놓기, 완료 확인이 필요합니다. 이 모두를 동시에 개선하면 실패 원인을 찾기 어렵습니다.

연구 질문은 이 목표에서 **원인이 궁금한 작은 관계**를 떼어냅니다.

| 구분 | 예 | 확인하는 방법 |
|---|---|---|
| 제작 목표 | 택배 분류 파이프라인을 실행한다 | 기능 점검과 작업 시연 |
| 연구 질문 | 목표 자리가 점유되었을 때, 실행 전 검사가 같은 예산에서 완료율을 높이는가? | 점유 정도를 바꾸고 검사 유무를 비교 |
| 설명 가설 | 검사로 불가능한 배치를 먼저 피하면 낭비가 줄지만, 과도한 검사는 추가 이동을 만든다 | 성공과 비용을 함께 측정하고 반례를 조사 |
| 연구 결과 | 어떤 조건에서 효과가 있었고 언제 비용이 더 컸는지 | 독립 평가 장면의 수치·불확실성·실패 기록 |

“VLM과 VLA를 연결한다”는 구현 목표입니다. “연결했으므로 더 지능적이다”는 아직 검증되지 않은 주장입니다. 목표가 분명한 고정 규칙이라면 간단한 프로그램이 강한 기준선일 수 있습니다. VLM의 가치는 명령 표현 변화나 모호한 표지 해석처럼 그 역할이 필요한 조건에서 따로 물어야 합니다.

## 2. 현재 코드가 표현하는 로비의 범위

현재 기반은 MuJoCo의 테이블과 단순 물체입니다. 정리 규칙에는 물체별 **고정 home 구역과 지정 자리**가 있습니다. 같은 구역 안의 아무 빈 곳이나 골라 놓는 문제와 다릅니다. 연구 실행기의 공통 검증은 규칙에 어긋난 목적지를 거절합니다. 모델이 목적지를 틀렸는데 정답으로 고쳐 실행한 결과를 모델의 정확도로 세지 않습니다.

실제 택배에서는 상자가 다른 상자를 지지하고, 꺼내면 무너질 수 있으며, 라벨이 가려지고 크기·무게·마찰이 다릅니다. 현재 평면 물체 실험은 이런 **3차원 적층의 해체·안정성**을 검증하지 않습니다. 그림에서 물체가 겹쳐 보이는 것과 실제로 위아래로 쌓인 것은 다릅니다.

가능한 단계는 다음과 같습니다.

1. 평면 단순 상자로 목적지 점유와 운반 순서의 영향을 알아낸다.
2. 크기·간격·관측 오차 중 하나를 추가해 원리가 유지되는지 시험한다.
3. 진짜 적층을 연구하려면 높이, 지지 관계, 제거 후 붕괴와 안전한 놓기를 구현하고 성공 판정부터 다시 검증한다.

3단계를 하지 않았다면 결론은 “기숙사 택배 분류를 단순화한 평면 시뮬레이션”으로 제한합니다. 현재 실행기는 운반을 중심으로 합니다. 임시 보관 위치나 밀기를 제안하려면 모든 비교 조건에 같은 행동 계약과 위치 검증을 확장해야 합니다.

## 3. 선행연구가 있다는 것은 무엇을 뜻할까?

[SayCan](https://say-can.github.io/)은 언어적 적합성과 실행 가능성을 결합했고, [Inner Monologue](https://innermonologue.github.io/)는 실행 피드백을 계획에 반영했습니다. [Code as Policies](https://code-as-policies.github.io/)는 언어와 기존 인식·제어 기능을 프로그램으로 연결했습니다. 따라서 “접근성을 검사했다” 또는 “실패 후 다시 계획했다”만을 세계 최초 아이디어로 내세우기는 어렵습니다.

그러나 선행연구가 모든 상자, 모든 정보 조건, 모든 예산에서 답을 주었다는 뜻도 아닙니다. 읽을 때는 저자의 **과제·입력 정보·행동·비교 방법·성공 기준·다루지 않은 조건**을 표로 적으세요. 우리 조건과 실제로 겹치는지 확인해야 합니다. 기숙사라는 이름만 바꾸는 것으로 학술적 차이가 생기지는 않지만, 이 환경에서 중요한 제약을 새로 정의하고 그 영향을 검증하는 것은 구체적인 연구 질문이 될 수 있습니다.

학생이 스스로 질문과 실험을 구성한 교육적 독창성과, 기존 지식에 새 기여를 보탠 학술적 독창성은 구분합니다. 새로운 알고리즘을 반드시 만들어야 하는 것은 아닙니다. 수상 여부는 대회별 기준과 연구 완성도에 달려 있으며, 모델의 최신성이나 이 문서의 체크리스트로 보장할 수 없습니다.

## 4. 질문을 여러 방향으로 열어 보기

아래 후보를 모두 수행하지 마세요. 자원과 현재 구현을 고려해 핵심 질문 하나와 작은 확장 하나를 선택합니다.

| 방향 | 작은 질문 | 가능한 반대 설명·주의점 |
|---|---|---|
| 접근 여유 | 손가락 여유 검사에서 어떤 간격에 오거절이 늘어나는가? | 저수준 제어가 이미 우회해서 검사가 불필요할 수 있음 |
| 목적지 점유 | 목표 자리 점유를 고려한 순서가 전체 분류를 돕는가? | 추가 이동이 짧은 예산에서는 손해일 수 있음 |
| 재계획 | 실패 원인에 따른 계획 갱신이 같은 행동 재시도보다 나은가? | 단순히 시도 기회를 더 받은 효과일 수 있음 |
| 식별과 판단 보류 | 읽기 어려운 라벨에서 재관측·보류가 오배송을 줄이는가? | 아무것도 보내지 않아도 오배송률은 낮아짐; 처리량을 함께 봄 |
| 정보 오차 | 좌표 오차가 커질 때 검사 여유를 늘리는 것이 언제 도움이 되는가? | 정확한 상태에서만 유리한 기준일 수 있음 |
| 명령 변화 | 구역 배정 규칙이 바뀌면 VLM은 고정 규칙보다 어떤 이점이 있는가? | 숨겨진 정답 대응표를 한 조건에만 주면 불공정 |
| 데이터 효율 | 같은 수집 시간에서 직접 시연과 검증한 역방향 시연이 어떻게 다른가? | 프레임 수가 같아도 독립 작업 다양성과 오류율이 다름 |
| 확장 과제 | 적층 지지 관계를 고려한 선택이 붕괴·재처리를 줄이는가? | 현재 적층 구현이 없어 환경·지표 확장이 먼저 필요 |

현재 구현에서 우선 추천하는 질문은 “출발지 접근성과 목적지 점유를 함께 고려한 선택이, 출발지만 보는 선택보다 미완료와 불필요한 이동을 줄이는가?”입니다. 출발지 간섭 없음/있음과 목적지 점유 없음/있음을 조합한 네 조건에서 비교하면 어느 제약이 영향을 주는지 분리할 수 있습니다. 이는 검증할 후보이며 정답이 아닙니다. 적층으로 확장할 때는 지지 관계가 추가되므로 별도 구현·검증이 필요합니다.

처음에는 “무엇이 실패하는가?”라는 탐색 질문으로 시작해도 됩니다. 작은 파일럿에서 실패를 분류한 뒤 가설을 세울 수 있습니다. 탐색 결과를 본 뒤 세운 가설은 **새 평가 데이터**로 확인합니다. 관찰 후 만든 설명을 처음부터 예측한 가설처럼 쓰지 않습니다.

## 5. 검증 가능한 가설을 만드는 방법

좋은 가설에는 대상 조건, 비교 방법, 예상 방향, 그 이유, 틀릴 수 있는 조건이 있습니다. “성능이 좋아질 것이다” 대신 다음처럼 적어 보세요.

> 지정 목적지 점유가 있는 평면 장면에서는, 실행 전 점유 검사와 다음 행동 선택을 사용하면 검사 없는 방법보다 동일한 전체 실행 예산에서 장면 완료율이 높아질 것으로 예상한다. 점유된 자리에 대한 반복 운반을 줄이기 때문이다. 반면 열린 장면에서는 보수적인 검사 때문에 불필요한 이동이나 보류가 늘어날 수 있다.

이는 검사를 쓰면 반드시 좋아진다는 약속이 아닙니다. 실행 제어기가 충돌을 알아서 해결하거나 검사 오거절이 많으면 차이가 없거나 나빠질 수 있습니다. 이런 반례가 연구의 중요한 결과가 됩니다.

**실행 전 작성하는 설계 예시 — 아직 측정 결과 없음**

| 항목 | 채운 예시 |
|---|---|
| 연구 대상 | 평면 상자 4개, 고정 home 자리, 고전 운반 제어기 |
| 바꿀 변인 | 목표 자리 점유 유무, 검사 유무 |
| 고정할 조건 | 초기 물리 상태, 공개 정리 규칙, 제어기, 전체 스텝·시도·계획 호출 예산 |
| 주 결과 | 예산 안에 모든 상자가 올바른 곳에 안정적으로 놓인 장면의 비율 |
| 보조 결과 | 미완료 물체 수, 추가 이동, 시도 수, 계획 호출 수, 시간 |
| 기전 예측 | 검사 조건에서 점유된 목적지에 대한 무효 시도가 줄어듦 |
| 반대 결과 | 열린 장면에서 성공은 같고 이동만 늘거나, 점유 장면에서도 효과 없음 |
| 비교 단위 | 독립 초기 배치 하나에 두 방법을 각각 적용한 쌍 |
| 기준 선택 | 파일럿·validation에서 정하고 최종 평가 전에 고정 |
| 주장 범위 | 정확한 상태를 사용하는 이 시뮬레이션 과제에 한정 |

“얼마나 좋아져야 실제로 쓸 만한가?”도 미리 정하세요. 예를 들어 오배송 감소와 추가 소요 시간 사이의 허용 범위를 정할 수 있습니다. 값은 운영 목적과 파일럿 측정으로 정당화해야 합니다. 원하는 결과가 나오도록 나중에 바꾸지 않습니다.

## 6. 측정할 말을 먼저 정의하기

“잘 잡았다”, “안전하다”, “분류했다”는 사람마다 다르게 셀 수 있습니다. 코드로 어떻게 판정할지 적고, 영상과 실제 상태를 대조해 판정기 자체를 점검합니다.

| 말 | 실험에서 필요한 정의 |
|---|---|
| 한 물체 운반 완료 | 실제 놓기 이후 올바른 구역·허용 높이·안정 조건 만족; 잠깐 들거나 손에 쥔 채 도착한 것과 구분 |
| 전체 장면 완료 | 평가 대상 모든 물체가 완료 조건 만족; 처음부터 제자리인 물체를 새 운반 성공으로 세지 않음 |
| 오배송 | 옮긴 뒤 공개 배정 규칙상 잘못된 구역에 안정적으로 놓음 |
| 보류·거절 | 실행하지 않기로 한 판단; 불가능한 작업의 올바른 거절과 가능한 작업의 오거절을 구분 |
| 접근성 오판 | 검사 판정과 검증된 실행 가능성의 불일치; 한 번 실패가 원천적 불가능을 증명하지 않음 |
| 복구 | 사전에 정의한 초기 실패 이후 같은 전체 예산 안에서 목표 달성 |
| 비용 | 제어 스텝, 벽시계 시간, 계획 호출, 추가 이동, 사람의 수집·검수 시간을 필요에 따라 분리 |

상자가 여러 개면 전체 완료율, 물체별 올바른 배달률, 오배송률을 함께 볼 수 있습니다. 모두 다른 지표입니다. ID 인식 F1은 배달 성공률이 아니며, 학습 loss는 작업 성공률이 아닙니다. 완료한 장면만 골라 시간을 비교하면 실패한 방법이 빠져 유리해질 수 있습니다. 시간 제한 실패도 포함해 완료율과 시간 분포를 함께 제시하세요.

알고리즘이 사용하는 실패 검출기와 최종 평가 판정기는 역할이 다릅니다. 전자는 실제 사용 가능한 센서 정보로 판단하고, 후자는 정답 상태로 실제 결과를 측정할 수 있습니다. 정답 결과를 몰래 다음 행동 선택에 넘기면 주장하는 정보 조건이 달라집니다.

## 7. 효과의 원인을 분리하는 비교

[학생 설계 코드](../vlapipe/student_design.py)의 세 함수에서 접근 판정, 다음 행동 선택, 계획 갱신 조건을 설계합니다. 기반 코드는 A 모드부터 실행할 수 있습니다.

| 조건 | 실행 전 검사 | 실행 결과에 따른 갱신 |
|---|---:|---:|
| A | 없음 | 없음 |
| B | 있음 | 없음 |
| C | 없음 | 있음 |
| D | 있음 | 있음 |

이 비교는 두 기능을 분리하는 출발점입니다. “원인을 이해한 재계획”을 주장하려면 **같은 예산의 단순 재시도**를 추가해야 합니다. 또 복잡한 제안 방법은 단순 거리·간격 검사나 간단한 규칙 순서와 비교해야 합니다. 쉬운 기준선도 같은 정보를 받아야 합니다. D가 A보다 좋다는 사실만으로 VLM이나 학생의 세부 선택 규칙이 원인이라고 말할 수 없습니다.

전체 실행 예산, 물체별 시도 상한, 계획 호출 상한을 각각 기록합니다. 동일한 상한이라도 실제 사용량은 다를 수 있으므로 사용량도 보고합니다. 추가 시도를 허용한 조건은 별도 예산 실험으로 구분하세요. 기능 하나를 제거하는 ablation은 “이 부분이 없으면 어떤 결과가 달라지는가?”를 묻는 실험입니다.

현재 `oracle_transport`는 정확한 물체와 목적지를 주는 진단 조건이며, 접근 순서까지 정답으로 주지는 않습니다. 현재 장면 좌표도 시뮬레이터의 정확한 상태입니다. VLM을 연결하는 연구 경로에는 이미지 외의 기하 상태·규칙 등도 제공됩니다. 따라서 그 결과는 이미지 단독 지능의 증거가 아닙니다. 정확한 상태로 로직을 확인한 뒤, 동일한 좌표 잡음이나 동일한 추정기를 모든 조건에 적용하면 오차 영향으로 질문을 확장할 수 있습니다.

## 8. 표본 수보다 먼저 독립성을 확인하기

한 장면의 1000프레임은 독립 장면 1000개가 아닙니다. 같은 배치에서 반복 실행하면 실행 변동을 알 수 있지만 공간 배치의 일반화 범위는 늘어나지 않습니다. 현재 고정 진단 장면은 seed를 3으로 나눈 나머지에 따라 위치가 반복됩니다. seed 이름 30개를 사용해도 독립 배치 30개가 아닙니다. 보고서의 `initial_geometry_sha256`와 실제 좌표로 중복을 확인하세요.

장면별로 A/B/C/D를 **같은 초기 상태에서 별도로 시작**해 비교하고, 장면별 차이를 분석합니다. 순서와 난수 영향도 통제·기록합니다. 여러 상자·하위 작업을 장면과 무관한 독립 표본으로 계산하지 마세요. 반복 실행을 했다면 배치 수와 배치당 반복 수를 따로 적습니다.

학습·기준 선택·최종 평가를 분리합니다. 같은 원본 장면의 프레임, 연속 구간, 역방향 변환 시연을 서로 다른 분할에 넣으면 누수가 생길 수 있습니다. **원본 장면·시연 가족 단위**로 묶어서 나누세요. 장면 일반화를 주장하려면 평가 배치도 학습·선택 장면과 독립이어야 합니다.

표본 수는 무조건 30이면 충분하다는 규칙으로 정하지 않습니다. 파일럿의 변동, 기대 효과, 구할 수 있는 독립 장면 수, 신뢰구간의 폭을 고려해 계획합니다. 장면별 짝 차이와 그 불확실성을 제시하고, 신뢰구간 계산은 장면 단위를 유지합니다. 실패가 드문 조건에서는 표본이 더 필요할 수 있습니다.

## 9. 실행 순서와 중간 통과 조건

1. **관찰·파일럿:** 쉬운 장면과 실패 장면을 직접 확인합니다. 설치 오류, 제어 오류, 계획 오류, 관측 오류를 분리합니다. 인위적 timeout 주입은 복구 경로 점검용이며 자연 실패율 측정이 아닙니다.
2. **질문 선택:** 한 문장 질문, 대안 설명, 반대 결과, 지표와 정보 조건을 워크시트에 작성합니다. 탐색 질문이면 무엇을 분류·기술할지 정합니다.
3. **최소 구현:** 세 함수를 작게 구현합니다. 어떤 입력에서 어떤 결정을 하는지 손으로 따라가고, 열린 장면을 부당하게 막는 반례도 만듭니다.
4. **데이터·학습:** 사용할 경우 시연을 검수하고 원본별 분할을 먼저 합니다. 기본 모델과 학습 모델을 같은 데이터·입력·출력 규격에서 비교합니다. 수집 시간과 검수 탈락도 기록합니다.
5. **validation:** 기준과 모델을 선택하고 판정 오류를 점검합니다. 이 장면은 이제 최종 독립 평가용이 아닙니다.
6. **설정 고정:** 코드 commit, 모델 ID/해시, 프롬프트, seed·배치 목록, 예산, 주 지표, 제외 규칙을 저장합니다.
7. **test:** 고정한 설정을 새 장면에서 실행합니다. 오류·실패를 포함한 원본 결과를 보존합니다. 조건마다 유리한 장면을 골라내지 않습니다.
8. **분석·후속 실험:** 가설과 다른 결과의 원인을 확인합니다. test를 보고 수정했다면 그 결과는 개발 자료가 됩니다. 새 holdout으로 다음 주장을 평가하세요.

현재(2026-11-05) VLM의 1스텝, VLA의 2스텝 학습·저장·재로딩 검사는 연결이 동작하는지 확인한 수준입니다. 작업 능력 향상이나 안정적인 VLM→VLA 분류 성공을 입증한 모델이 아닙니다. 완성된 연구 결과로 인용하지 마세요. 먼저 독립된 열린 장면에서 저수준 제어기가 실제 운반을 수행하는지 확인해야 합니다. 아직 VLA가 준비되지 않았다면 고전 제어기에서 계획 질문을 검증하고 사용한 제어기를 정확하게 밝힐 수 있습니다.

텔레옵·수집은 [학생 텔레옵 안내](../TELEOP_STUDENT.md), 환경 구성은 [설치 안내](../SETUP_STUDENT.md)를 따릅니다. 키보드로 같은 게임패드 입력 처리 경로를 점검하는 것과 실제 USB 조이스틱으로 파지 시연을 검증하는 것도 구분하세요.

## 10. 예상과 다른 결과를 해석하기

세 가지 문장을 구분하세요.

- “검사 조건의 완료율이 낮았다”: 관측 결과입니다.
- “오거절이 원인일 수 있다”: 설명 가설입니다.
- “오거절된 장면을 따로 조사하고 기준을 완화한 후 새 평가 장면에서 회복되었다”: 추가 근거입니다.

예상한 차이가 없다고 가설이 곧 반증되는 것은 아닙니다. 표본이 작거나 측정이 거칠면 효과를 가려낼 힘이 부족할 수 있습니다. **통계적으로 유의하지 않다는 사실은 두 방법이 같다는 증거가 아닙니다.** 효과 추정치와 신뢰구간이 실제로 의미 있는 개선·악화 범위를 얼마나 포함하는지 보세요. 가설을 반박하는 방향의 충분히 정밀한 결과인지, 판단할 수 없는 결과인지 나눠 설명합니다.

반대로 큰 차이가 나와도 대조 조건에 더 적은 정보나 예산을 주었다면 방법 자체의 효과로 해석할 수 없습니다. 판정기가 잘못되었거나 구현이 가설대로 동작하지 않았다면 가설의 옳고 그름부터 결론내리지 말고 실험의 타당성을 먼저 고칩니다.

역방향 데이터도 마찬가지입니다. 액션 배열의 부호를 바꾸어 되돌렸다는 사실과 물체 접촉·잡기·놓기가 물리적으로 재현된다는 사실은 다릅니다. 한 구현의 역재생 실패는 모든 역방향 학습 방법이 불가능하다는 증거가 아닙니다. 검증한 시연만 학습에 쓰고 실제 재생·물체 종점·성공 판정을 확인해야 합니다.

## 11. 도움을 받으면서도 자기 연구로 만드는 법

조교가 환경, 수집·학습 도구, 공통 실행기와 진단 예시를 제공할 수 있습니다. 여러분은 질문 선택, 변인·지표 정의, 판단 규칙과 반례 설계, 실험 수행·분석에서 실제 선택을 해야 합니다. 모든 코드를 혼자 처음부터 쓰는 것이 자기주도성의 조건은 아닙니다.

연구일지에는 “누가 어떤 도움을 주었나”, “내가 결정한 것은 무엇인가”, “어떤 관찰 때문에 바꿨나”를 남깁니다. 조교 코드와 AI가 생성한 코드도 출처와 수정 범위를 적고, 핵심 함수의 입력·출력·한계를 직접 설명하고 검증하세요. 완성 참조 코드를 실행한 것을 독자 알고리즘으로 쓰지 않습니다.

실제 택배 라벨에는 개인정보가 있습니다. 초기에는 가상 수취인·합성 라벨을 사용하고 실제 이름·주소가 데이터나 공개 저장소에 들어가지 않게 하세요. 원본 데이터는 지우지 않고 새 결과 폴더를 사용합니다. 코드, 데이터, 가중치의 버전과 이용 조건을 따로 기록하면 공동작업과 재현이 쉬워집니다.
