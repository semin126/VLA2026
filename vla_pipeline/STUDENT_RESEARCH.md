# 접근성 검사와 재계획: 학생 실험 시작 안내

GPU 없는 Windows·VS Code 환경에서는 [Final_project 시작 안내](docs/FINAL_PROJECT.md)를 사용하세요. 연구 판단의 한 장 요약은 [여섯 가지 지점](docs/RESEARCH_DECISIONS.md)입니다.

기반 코드는 설치, 이미지·상태 처리, 제어, 기록, 실행 예산을 제공합니다. 여러분이 설계할 부분은 `vlapipe/student_design.py`의 세 함수입니다. 정답 코드 하나를 맞히는 과제가 아닙니다. 선택한 규칙이 어떤 조건에서 실패할지 먼저 예측하고 대조 실험으로 확인하세요.

## 먼저 빈칸 없이 기준선을 실행하기

PowerShell에서 `vla_pipeline`을 작업 폴더로 사용합니다. 매 실행의 `--out`에는 새 경로를 지정하세요.

```powershell
& .\.venv\Scripts\python.exe scripts/run_research_lab.py --mode A --case open --out outputs/my_lab_open_A
```

기본 계획은 시뮬레이터에서 잘못 놓인 물체 목록만 얻는 `oracle_transport`입니다. 접근성 순서를 정답으로 제공하지 않습니다. 저수준 동작은 정확한 위치를 사용하는 고전 제어기입니다. 이 기준선의 성공을 VLM/VLA 학습 성공으로 보고하면 안 됩니다.

## 여러분이 결정할 세 가지

| 함수 | 결정할 내용 | 먼저 작성할 연구 질문 |
|---|---|---|
| `assess_accessibility` | 지금 집고 놓을 수 있는지, 어떤 물체가 방해하는지 | 보이는 물체와 실제 잡을 수 있는 물체는 어떻게 다른가? |
| `choose_next` | 다음 물체·방해물 선택, 행동을 보류할 조건 | 방해물을 옮기면 항상 이득인가? |
| `should_replan` | 실행 결과를 보고 언제 다시 계획할지 | 모든 동작 뒤 재계획하면 어떤 비용이 생기는가? |

각 함수의 입력·출력 설명은 코드 안에 있습니다. 장면에는 물체 위치·방향·크기·보관 구역·지정 배치 위치가 있습니다. 현재 이 정보는 시뮬레이터 정답 상태입니다. 모든 비교 조건에 같은 상태를 제공하며, 이미지에서 접근성을 추정했다고 주장하지 않습니다.

## 기능을 한 가지씩 비교하기

| 모드 | 접근성 검사 | 결과에 따른 재계획 |
|---|---:|---:|
| A | 끔 | 끔 |
| B | 켬 | 끔 |
| C | 끔 | 켬 |
| D | 켬 | 켬 |

함수를 작성한 뒤 다음과 같이 선택합니다. 미완성 함수는 `NotImplementedError`로 멈춥니다. 이를 패키지 설치 오류로 오인하지 마세요. A 기준선은 세 함수를 채우기 전에도 실행됩니다.

```powershell
& .\.venv\Scripts\python.exe scripts/run_research_lab.py --mode D --design student --case blocked --out outputs/my_lab_blocked_D
```

`open`, `blocked`, `destination_blocked`, `unreachable`은 미리 정의한 작은 장면입니다. 이름이 blocked라고 해서 실제 파지가 반드시 실패하는 것은 아닙니다. 기하학적 검사와 실제 제어 결과가 다를 수 있으며, 그 차이를 분석하는 것이 과제입니다. `messy`, `cluttered`도 선택할 수 있습니다.

고정 진단 장면은 seed를3으로 나눈 나머지에 따라 세 가지 y 위치만 사용합니다. seed 이름30개를 실행해도 독립 배치30개가 되지 않습니다. report의 initial_geometry_sha256이 같으면 같은 배치로 묶으세요. 본 실험의 장면 변화·간격·배치는 별도로 설계하거나 messy/cluttered의 실제 다양성을 확인한 뒤 사용합니다.

## 공정하게 고정할 것

같은 seed, 물체 수, 저수준 제어기, 전체 스텝 예산을 사용하세요. 기본값은 물체 4개입니다. 동일 물체의 재시도와 모델 호출 수는 상한이 있으므로 무한 반복하지 않습니다. 예산·관측 조건을 바꾼 결과는 별도 실험으로 기록합니다.

`--fault timeout_first_action`과 `--fault empty_first_plan` 등은 복구 경로가 동작하는지 확인하는 인위적 진단입니다. 이 결과를 모델의 자연적인 실패율이나 일반적인 개선 성능으로 보고하지 않습니다. 정상 실험은 `--fault none`입니다.

## 모델을 연결하는 단계

설계 원리를 고전 제어기에서 확인한 뒤 `--planner vlm --vlm-model <모델경로>`를 추가할 수 있습니다. 기본 `--prompt-style number`는 목적지까지 VLM이 말합니다. `number_read`는 숫자 목록을 받고 공개 규칙으로 목적지를 정하는 별도 조건입니다. VLM이 빈 계획을 내도 정답 계획으로 바꾸지 않습니다. 모든 모드의 VLM에는 같은 이미지와 같은 위치·크기·보관 규칙·그리퍼 치수 정보를 줍니다. 접근성 판정 결과나 정답 행동 순서는 제공하지 않습니다.

현재 연습 과제는 고정 home 구역·지정 슬롯으로 정리하는 과제입니다. 알려지지 않은 물체, 잘못된 구역, 공개 정리 규칙을 위반한 목적지, 지원하지 않는 행동은 A/B/C/D 공통 입력 검증에서 이유와 함께 기록하고 거절합니다. 잘못된 목적지를 정답으로 고쳐 실행하지 않습니다. 임시 중앙 배치 등 다른 행동을 연구하려면 이 공통 과제 계약과 놓을 위치 계산을 모든 조건에 동일하게 확장해야 합니다.

유효한 하위 작업 VLA 체크포인트가 준비되면 `--policy smolvla --checkpoint <경로>`를 사용합니다. 기반 검사와 실제 작업 성능을 구분하세요. 전체 장면 결과는 목표 구역, 물체 높이, 실제 손가락 열림을 검사합니다. 이미 목표 구역에 놓인 물체를 새 운반 성공으로 세지 않습니다.

## 기록할 것

결과 폴더의 `report.json`과 시작·종료 이미지를 보관하세요. 보고서에는 가설, 바꾼 규칙, 코드 버전, seed, 성공 기준, 전체 스텝, 모델 호출 수, 실패 사례를 함께 남깁니다. 한 조건이 좋아지지 않았을 때 결과를 지우거나 장면을 유리하게 골라 다시 성공률을 계산하지 않습니다.
